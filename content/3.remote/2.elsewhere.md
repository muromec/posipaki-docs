# Running an actor elsewhere

> `posipaki-remote-ssh` and `posipaki-remote-podman` are the ways *out*: an actor
> on another machine, or inside a container. The seam is the same one
> [Remote Actors](/remote/) describes — a spawner returns a `Channel` — so your
> code keeps talking to a proxy and never to a transport.

```sh
npm install posipaki posipaki-remote-ssh
npm install posipaki posipaki-remote-podman
```

Both are versioned in lockstep with the core: a payload's only claim is which
posipaki it speaks, so the package and the core it builds against ship together.
`LIB_VERSION` from `posipaki` is that version.

## Two facts about a foreign environment

Everything these packages do follows from two properties of a context that is not
your process.

1. **The only channel every way in gives you is the stdio of the command that gets
   you in.** A path created here does not exist there, and a path created there is
   not yours to open. The wire is a pipe: your child's stdin and stdout.
2. **Nothing of yours is on the other side yet.** The actor's code has to arrive
   before it can run — and the step that delivers it cannot carry the wire, because
   its own stdin *is* the script.

So a spawn is two stages: a command that puts the payload somewhere and reports
what it found, then a command whose own stdin/stdout are the wire.

## Over ssh

```ts
import { remoteClient } from "posipaki/remote";
import { sshSpawner } from "posipaki-remote-ssh";

const spawner = sshSpawner<ToolArgs>(
  {
    host: "toolbox",                                 // whatever ssh accepts
    app: { name: "my-app", version: "1.4.0" },       // who stages, and which build
    payload: "build/env-payload.js",                 // the bundle to put up there
  },
  {
    // The payload's own arguments — this package does not know what they mean.
    args: (boot) => [`--env=${boot.env}`],
    onGone: (host) => console.warn(`${host} is gone`),
  },
);

const env = await root.fork(remoteClient("tools", spawner), { env: "agent" });
```

What runs:

```sh
ssh toolbox sh -s                                  # the bootstrap, script on stdin
ssh toolbox /usr/bin/node ~/bin/posipaki/<kit>/payload.js --env=agent
```

The kit lands in `$HOME/bin/posipaki/<app>-<version>-posipaki-<core version>-<hash>/`
on the far side, one directory per build, so two consumers or two releases cannot
land on each other's files. Staging is idempotent: the script probes, writes only
what is missing, tries the runtimes in order (`node`, `nodejs`, `bun` by default)
and reports one line per step.

`relay: true` (with `gateway`) runs the payload behind posipaki's gateway, which
creates a fifo *inside* the host and relays to it. Reach for it when the payload
may print — its own stdout would otherwise be the wire — or when the host is
reached as another uid, which could not open a fifo you created here.
## In a container

A container is two things, and this package keeps them apart: the container
itself, which has a life, and a way into it, which does not.

```ts
import {
  containerActor,
  podmanConnector,
  podmanCopy,
  podmanEnvironment,
} from "posipaki-remote-podman";

// an actor that is already in the image
const spawner = podmanConnector<ToolArgs>({
  container: "env-agent",
  command: (boot) => ["/usr/local/bin/worker", `--pool-size=${boot.poolSize}`],
});

// or one that copies itself in first: the kit is staged, then run by a runtime
const copying = podmanCopy<ToolArgs>(
  {
    image: "toolbox:1",
    container: "env-agent",
    app: { name: "my-app", version: "1.4.0" },
    payload: "build/env-payload.js",
  },
  { args: (boot) => [`--pool-size=${boot.poolSize}`] },
);
```

| Piece | What it is |
| --- | --- |
| `containerActor` | a container, as an actor: it starts one, holds it while it lives, counts the consumers that retain it, and lets it go at the end |
| `podmanConnector` | the way in by name — a prepare step (optional) and a command, on the `exec`'s own stdin/stdout. No container, no channel |
| `podmanCopy` | the connector with the actor staged into the container first |
| `podmanEnvironment` | both together: a container of its own for one actor, started for it and let go when it is done — and, since that container exists for the actor, one we take over rather than refuse |

The container's name is yours to give, and there is no default: a name taken from
the image would be a guess, and a name is what decides who else ends up in there.
Two apps naming the same container share it — its mounts, its user, its network —
so that is a decision, not a fallback.

### The container's life

The policy is one sentence — *the environment is a process-tree child of whoever
holds it*:

- the container is started by an **attached** `podman run` whose main process does
  nothing but read its stdin;
- while you live, that read blocks and `podman exec` can open as many channels into
  the container as you like;
- when you go — clean exit, SIGTERM, SIGKILL — the write end closes, the reader sees
  EOF, and `--rm` takes the container with it.

Nothing has to remember to clean up, though the container goes a moment after you
do, once podman has reaped it, not in the same instant. Sharing works the same way:
`containerActor` counts the consumers that retain it, and the last release — or the
actor's own end — lets the container go.

```ts
const container = await containerActor.spawn({ image: "toolbox:1", container: "env-agent" });
container.send({ type: "RETAIN" });   // UP, RETAINED and STATUS come back
container.send({ type: "RELEASE" });  // the last one out takes the container down
```

A name that is already taken by a container this process is not holding is **never
adopted** in silence — the holder is somebody else's process, and their lifetime is not
yours to own. `onConflict` says what to do instead: `fail` (say what was found and stop),
`reuse` (run in theirs and hold nothing — a wanted name gets a moment to be freed first,
since a container goes a moment after its holder), or `replace` (remove what is there and
start your own, for containers you assume you manage).

Which one is the default follows from whose container it is. The container actor holds
`fail`: a container it did not start is somebody else's, and it is not for us to end it.
`podmanEnvironment` holds `replace`, because its container *is* the actor's — it was
started for that actor, so a name already in use is a leftover to take over rather than
a wall to stop at. An environment that must not do that passes `fail` or `reuse`
explicitly.

Both packages also expose the pieces separately, for pre-warming or your own wiring:
`sshStage` / `podmanStage` (put the kit there, report where), `sshKit` / `podmanKit`
(build the kit from your bundles) and, for podman, `startContainer` /
`stopContainer` / `removeContainer` / `containerExists`.

## How failures read

A way in that fails fails loudly and quickly: the reason is what the host said.

```text
ssh env.invalid is not available: the host exited with code 255: ssh: connect to host env.invalid port 22: Connection refused
staging into container env-agent failed: no runtime among: node nodejs bun
```

The command's own stderr is *not* the wire, so it is collected, forwarded to a sink
(`onOutput`, our stderr by default, tagged with the host) and its tail becomes the
reason. A channel that closes tells the caller through `onGone`, so a slot can stop
pointing at a process that is gone.

## Testing your own way in

Every host interaction is injected — `runHost` (one command), `startHost` (the
container's process), `spawnChild` (the wire's process) — so a suite stages and
spawns with no ssh and no podman installed, asserting the commands and what travels
on stdin. A real host is an opt-in integration test.

```ts
const commands: string[][] = [];
const spawner = sshSpawner(spec, {
  runHost: async (command, stdin) => {
    commands.push(command);
    return { code: 0, stdout: "present\nkit /home/u/bin/posipaki/<kit>\nruntime node\n", stderr: "" };
  },
  spawnChild: (command, stdio) => spawn(process.execPath, [farEnd], { stdio }),
});
```

## Where each piece lives

| piece | where |
| --- | --- |
| the wire, the kit vocabulary, the gateway | `posipaki/remote/node` |
| the commands, the kit, staging, the spawner, the container's actor | `posipaki-remote-ssh`, `posipaki-remote-podman` |
| what runs inside — your actor, its tools | your bundle |

The two packages deliberately duplicate their shape rather than share it: a way in
is a way in, and an abstraction over exactly what differs helps nobody. Adding
`bwrap` later follows the same shape.
