# Running an actor elsewhere

> `posipaki-remote-ssh`, `posipaki-remote-podman` and `posipaki-remote-bwrap` are
> the ways *out*: an actor on another machine, an actor in a container, an actor
> in a sandbox of this machine. The seam is the same one
> [Remote Actors](/remote/) describes — a spawner returns a `Channel` — so your
> code keeps talking to a proxy and never to a transport.

```sh
npm install posipaki posipaki-remote-ssh      # another machine
npm install posipaki posipaki-remote-podman   # a container
npm install posipaki posipaki-remote-bwrap    # this machine, with less of it in reach
```

All three are versioned in lockstep with the core: a payload's only claim is which
posipaki it speaks, so the package and the core it builds against ship together.
`LIB_VERSION` from `posipaki` is that version.

## Two facts about the far side

Everything these packages do follows from two properties of an environment that is
not your process.

1. **The only channel every way in gives you is the stdio of the command that gets
   you in.** A path created here does not exist there, and a path created there is
   not yours to open. The wire is a pipe: your child's stdin and stdout.
2. **Your code has to arrive before it can run.** The step that delivers it cannot
   carry the wire, because its own stdin *is* the script.

So a spawn is two stages: a command that puts your code there and reports what it
found, then a command whose own stdin/stdout are the wire.

What travels is a **kit**: your bundles, a manifest with one hash per file, and a
`version.json` naming the build. The far side writes a kit into one directory per
build, probes before it writes, and reports one line per step — so staging the same
build twice costs a probe and no writes. The vocabulary is the core's
(`posipaki/remote/node`); each package knows which files belong in a kit and under
which names.

## One shape, three ways in

| Package | Way in | What is out there |
| --- | --- | --- |
| `posipaki-remote-ssh` | `ssh [user@]host …` | another machine |
| `posipaki-remote-podman` | `podman exec -i <container> …` | a container |
| `posipaki-remote-bwrap` | `bwrap <policy> …` | this machine, with less of it in reach |

Two words carry that shape, and every package ships both of them:

- a **connector** is the way in: an optional `prepare` step and the `command` to
  run, both on the run's own stdin/stdout;
- a **bootstrap** is that connector with the kit staged first: `prepare` writes the
  kit and reports where it landed, `command` runs the payload with the runtime the
  staging found.

The names carry their package, so `sshConnector` / `sshBootstrap`,
`bwrapConnector` / `bwrapBootstrap`, `podmanConnector` / `podmanBootstrap`. Reach
for a connector when the far side already has what you want to run, and a bootstrap
when it has to be put there first.

## Over ssh

```ts
import { remoteClient } from "posipaki/remote";
import { sshBootstrap } from "posipaki-remote-ssh";

const spawner = sshBootstrap<ToolArgs>(
  {
    host: "toolbox",                                 // whatever ssh accepts
    app: { name: "my-app", version: "1.4.0" },       // who stages, and which build
    payload: "build/env-payload.js",                 // the bundle to put up there
  },
  {
    // The payload's own arguments — this package does not know what they mean.
    args: (boot) => [`--env=${boot.env}`],
    onGone: () => console.warn("toolbox is gone"),
  },
);

const env = await root.fork(remoteClient("tools", spawner), { env: "agent" });
```

| Piece | What it is |
| --- | --- |
| `sshConnector` | the way in by host — a prepare step (optional) and a command, on the run's own stdin/stdout |
| `sshBootstrap` | the connector with the actor staged onto the host first |

Two pieces here, because the ssh process *is* the lifetime: ssh has nothing to
start and nothing to hold. Podman has a container to hand over, and that is where
its other two pieces come from.

What runs:

```sh
ssh toolbox sh -s                                  # the bootstrap, script on stdin
ssh toolbox /usr/bin/node ~/bin/posipaki/<kit>/payload.js --env=agent
```

The kit lands in `$HOME/bin/posipaki/<app>-<version>-posipaki-<core version>-<hash>/`
on the far side, one directory per build, so two consumers or two releases land
next to each other. Staging tries the runtimes in order (`node`, `nodejs`, `bun` by
default) and reports the one it found.

`relay: true` (with `gateway`) runs the payload behind posipaki's gateway, which
creates a fifo *inside* the host and relays to it. Reach for it when the payload
may print — its own stdout would otherwise be the wire — or when the host is
reached as another uid, which could not open a fifo you created here.

## In a container

A container is two things, and this package keeps them apart: the container
itself, which has a life, and a way into it, which does not.

```ts
import {
  containerActor,
  podmanConnector,
  podmanBootstrap,
  podmanEnvironment,
} from "posipaki-remote-podman";

// an actor that is already in the image
const spawner = podmanConnector<ToolArgs>({
  container: "env-agent",
  command: (boot) => ["/usr/local/bin/worker", `--pool-size=${boot.poolSize}`],
});

// or one that is bootstrapped in first: the kit is staged, then run by a runtime
const bootstrapped = podmanBootstrap<ToolArgs>(
  {
    image: "toolbox:1",
    container: "env-agent",
    app: { name: "my-app", version: "1.4.0" },
    payload: "build/env-payload.js",
  },
  { args: (boot) => [`--pool-size=${boot.poolSize}`] },
);
```

| Piece | What it is |
| --- | --- |
| `containerActor` | a container, as an actor: it starts one, holds it while it lives, counts the consumers that retain it, and lets it go at the end |
| `podmanConnector` | the way in by name — a prepare step (optional) and a command, on the `exec`'s own stdin/stdout |
| `podmanBootstrap` | the connector with the actor staged into the container first |
| `podmanEnvironment` | both together: a container of its own for one actor, started for it and let go when it is done |

The container's name is yours to give, and a name is what decides who else ends up
in there: two apps naming the same container share it — its mounts, its user, its
network. The name is the decision, and the image follows from it.

### The container's life

The policy is one sentence — *the environment is a process-tree child of whoever
holds it*:

- the container is started by an **attached** `podman run` whose main process does
  nothing but read its stdin;
- while you live, that read blocks and `podman exec` can open as many channels into
  the container as you like;
- when you go — clean exit, SIGTERM, SIGKILL — the write end closes, the reader sees
  EOF, and `--rm` takes the container with it.

Nothing has to remember to clean up, though the container goes a moment after you
do, once podman has reaped it, not in the same instant. Sharing works the same way:
`containerActor` counts the consumers that retain it, and the last release — or the
actor's own end — lets the container go.

```ts
const container = await containerActor.spawn({ image: "toolbox:1", container: "env-agent" });
container.send({ type: "RETAIN" });   // UP, RETAINED and STATUS come back
container.send({ type: "RELEASE" });  // the last one out takes the container down
```

### A name that is already taken

When a container by that name is already running and this process is not holding
it, the holder is somebody else's process, and their lifetime is yours to end only
if you say so. `onConflict` says it:

- `fail` — report what was found and stop;
- `reuse` — run in theirs and hold nothing. A wanted name gets a moment to be freed
  first, since a container goes a moment after its holder;
- `replace` — remove what is there and start your own, for containers you assume you
  manage.

The default follows from whose container it is. `containerActor` holds `fail`,
because a container it did not start belongs to somebody else.
`podmanEnvironment` holds `replace`, because its container *is* the actor's — it was
started for that actor, so a name already in use is a leftover to take over. An
environment that must keep its hands off passes `fail` or `reuse` explicitly.

## In a sandbox

The same machine, with less of it in reach. `bwrap` binds paths and takes
namespaces away, so a sandbox is a policy plus a command — and it lasts exactly as
long as the command, which leaves nothing to start, hold or clean up.

```ts
import { remoteClient } from "posipaki/remote";
import { bwrapBootstrap, sandboxArgs } from "posipaki-remote-bwrap";

const spawner = bwrapBootstrap<ToolArgs>(
  {
    name: "tools",                                   // what errors and output are tagged with
    args: sandboxArgs({ home: "/srv/agent" }),       // the policy: what it may see and touch
    app: { name: "my-app", version: "1.4.0" },
    payload: "build/env-payload.js",
  },
  { args: (boot) => [`--env=${boot.env}`] },
);

const env = await root.fork(remoteClient("tools", spawner), { env: "agent" });
```

| Piece | What it is |
| --- | --- |
| `bwrapConnector` | the way in by policy — a prepare step (optional) and a command, on the run's own stdin/stdout |
| `bwrapBootstrap` | the connector with the actor staged in first |
| `sandboxArgs` | the policy this package suggests, and every part of it a knob |

What `sandboxArgs()` builds, and why each part is there:

- `--ro-bind / /` — the whole machine, read-only. Narrower binds come after it, and
  come out on top;
- `--bind <home> <home>` and `--setenv HOME <home>` — the one directory a payload
  may write to, and what it calls home. A staged kit lands there, and since bwrap
  binds rather than copies, the file on the inside *is* the file on the outside;
- `--dev /dev`, `--proc /proc`, `--tmpfs /tmp` — the few things a runtime needs to
  believe it is on a machine, all of them its own;
- `--unshare-pid --unshare-uts --unshare-ipc`, `--die-with-parent`,
  `--new-session` — its own namespaces, no process outliving ours, no terminal handed
  back;
- the network stays reachable, and `network: false` takes it away.

`args` is bwrap's own argument list, so a consumer who wants the host's network
gone, a socket mounted, or a read-only home says so. The package hands the policy to
bwrap and reports what bwrap said.

## The pieces on their own

Every package also exposes what it builds on, for pre-warming or your own wiring:
`sshStage` / `podmanStage` / `bwrapStage` put the kit there and report where,
`sshKit` / `podmanKit` / `bwrapKit` build a kit from your bundles, and podman adds
`startContainer` / `stopContainer` / `removeContainer` / `containerExists`.

## How failures read

A way in that fails fails loudly and quickly, and the reason is what the host said.

```text
ssh env.invalid is not available: the host exited with code 255: ssh: connect to host env.invalid port 22: Connection refused
staging into container env-agent failed: no runtime among: node nodejs bun
sandbox tools is not available: the sandbox exited with code 1: bwrap: Can't find source path /nope: No such file or directory
```

The command's own stderr is *not* the wire, so it is collected, forwarded to a sink
(`onOutput`, our stderr by default, tagged with the host) and its tail becomes the
reason. A channel that closes tells the caller through `onGone`, so a slot can stop
pointing at a process that is gone.

## Testing your own way in

Every host interaction is injected — `runHost` (one command), `startHost` (the
container's process), `spawnChild` (the wire's process) — so a suite stages and
spawns with no ssh, no podman and no bwrap installed, asserting the commands and
what travels on stdin.

```ts
const commands: string[][] = [];
const spawner = sshBootstrap(spec, {
  runHost: async (command, stdin) => {
    commands.push(command);
    return { code: 0, stdout: "present\nkit /home/u/bin/posipaki/<kit>\nruntime node\n", stderr: "" };
  },
  spawnChild: (command, stdio) => spawn(process.execPath, [farEnd], { stdio }),
});
```

A real host is an opt-in integration test: podman's runs behind
`POSIPAKI_PODMAN_IMAGE`, and bwrap's runs wherever `bwrap` is on the machine and
skips itself where it is not.

## Where each piece lives

| piece | where |
| --- | --- |
| the wire, the kit vocabulary, the gateway | `posipaki/remote/node` |
| the commands, the kit, staging, the connector and the bootstrap, the container's actor | `posipaki-remote-ssh`, `posipaki-remote-podman`, `posipaki-remote-bwrap` |
| what runs inside — your actor, its tools | your bundle |

Each package carries its own copy of the shape: three small files, no abstraction
grown over exactly what differs. All three come down to the same two knobs — a
`prepare` and a `command` — and take the same options. A fourth way in is a
connector, a bootstrap, and a kit to put there first.
