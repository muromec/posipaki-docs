# Remote Actors

Run an actor in another execution context — a child process, a WebSocket
connection, or a worker — and drive it exactly like a local spawn. The actor
doesn't know it's remote; your code doesn't either.

## The idea

A remote actor is a **server/client** pair speaking a small protocol:

- **Server** holds the real actor — `setup`, handlers, and its storage.
- **Client** holds a proxy. You `spawn`/`send`/`wait` on it as usual, and it
  bridges messages and state across the wire.

```ts
import { serveRemoteActor } from "posipaki/remote";   // server
import { remoteClient }     from "posipaki/remote";   // client
```

`serveRemoteActor(actor, spawner)` serves one actor over a channel. `remoteClient(name,
spawner)` returns a full `ActorDefinition` whose `spawn` connects and mirrors the
remote. A **spawner** is a transport factory — it obtains the channel and does
the version handshake, so the seam never knows which transport it's on.

## Subprocess — one file, both ends

The flagship use: the same module is the host *and* the child. Import
`defineSubprocessActor` from the node subpath, pass your actor and `import.meta.url`,
and it detects the child via a `--remote=<hash>` argv marker:

```ts
import { defineActor } from "posipaki";
import { defineSubprocessActor } from "posipaki/remote/node";

const echoActor = defineActor({
  name: "echo",
  setup: () => ({ pings: 0 }),
  handlers: {
    PING(msg) {
      this.state.pings++;
      this.emit({ type: "PONG", count: msg.count });
    },
  },
});

const { actor: remoteEcho, isRemoteRoot } = defineSubprocessActor(echoActor, import.meta.url);

if (!isRemoteRoot) {
  const proc = await remoteEcho.spawn({});
  await proc.ready();
  proc.send({ type: "PING", count: 1 });
  await proc.wait();
}
```

`defineSubprocessActor(actor, url, opts?)` returns:

- **`actor`** — a proxy `ActorDefinition`. Spawn it like any actor; the first
  thing it does is boot the child process and bridge messages.
- **`runRemoteRoot()`** — serve the real actor (run this when you are the child).
- **`isRemoteRoot`** — `true` when this process is the spawned child.

Pass `{ manual: true }` to disable argv auto-detection and call `runRemoteRoot()`
yourself. The runner is auto-detected (`bun` or `node`).

## WebSocket

Connect to a served actor from anywhere — including the browser:

```ts
import { remoteClient, wsClientSpawner } from "posipaki/remote";

const echo = remoteClient("echo", wsClientSpawner("ws://example.test/echo"));
const proc = await echo.spawn({});
await proc.ready();
proc.send({ type: "PING", count: 1 });
```

On the server side, `wsServerSpawner(ws)` serves an already-upgraded socket.
With Bun, `bunServerWebSocket(ws)` adapts the socket:

```ts
import { serveRemoteActor, wsServerSpawner, bunServerWebSocket } from "posipaki/remote";

Bun.serve({
  fetch(req, server) {
    if (server.upgrade(req)) return;
    return new Response("upgrade failed", { status: 400 });
  },
  websocket: {
    open(ws) {
      const adapter = bunServerWebSocket(ws);
      ws.data = adapter;
      serveRemoteActor(echoActor, wsServerSpawner(adapter));
    },
    message(ws, msg) { ws.data.onmessage?.({ data: msg }); },
    close(ws) { ws.data.onclose?.(); },
  },
});
```

## Workers

Workers pass frame objects by structured clone — no JSON round-trip. The worker
script serves itself with `workerSelfSpawner`:

```ts
// worker.js
import { serveRemoteActor, workerSelfSpawner } from "posipaki/remote";
import { echoActor } from "./echo.js";

serveRemoteActor(echoActor, workerSelfSpawner());
```

```ts
// main thread
import { remoteClient, workerClientSpawner } from "posipaki/remote";

const echo = remoteClient("echo", workerClientSpawner("./worker.js"));
const proc = await echo.spawn({});
```

## Building your own transport

The seam is transport-agnostic: `serveRemoteActor` and `remoteClient` speak
only in a `Channel` — decoded frame objects — plus the frame guards.
Everything below it is pluggable.

- **Protocol** — `json1Channel(transport)` wraps a `StringTransport` into a
  `Channel` with JSON encoding (`json.v1`).
- **Transport** — implement `StringTransport` (moves strings, for byte
  streams) or `Channel` (moves frame objects, for structured-clone
  `postMessage`).
- **Spawner** — a factory `() => Promise<Channel>` (server) or
  `(args) => Promise<Channel>` (client). It obtains the transport and
  performs the `$proto` handshake — send it on the server, validate it on
  the client.

```ts
import { serveRemoteActor, json1Channel, VERSION } from "posipaki/remote";

const mySpawner = async () => {
  const transport = yourStringTransport(); // e.g. a socket you opened
  const channel = json1Channel(transport);
  await channel.send({ $proto: VERSION });
  return channel;
};

serveRemoteActor(actor, mySpawner);
```

A worker transport skips JSON entirely: it implements `Channel` directly
and handshakes with `WORKER_VERSION` (`clone.v1`).

## Imports — portable vs node

The seam is split so a browser never drags in `node:fs`:

| Import | Contents | Runs in |
| --- | --- | --- |
| `posipaki/remote` | seam, WebSocket + worker transports and spawners | browser, service worker, node, bun |
| `posipaki/remote/node` | `defineSubprocessActor`, the FIFO transport, and its spawners | node, bun |

`posipaki/remote/node` additionally exposes the lower-level subprocess pieces —
`FifoUtf8NlineTransport`, `commandSpawner`, and `fifoArgvSpawner` — if you want
to hand-roll the FIFO bootstrap.

## Wire protocol

Server and client exchange five frames. Over FIFO and WebSocket they are
JSON-encoded (`json.v1`); over a worker they are structured-cloned (`clone.v1`).

| direction | frame | payload |
| --- | --- | --- |
| server → client | `$proto` | version (`json.v1` / `clone.v1`) |
| server → client | `$state` | state snapshot / update |
| server → client | `$msg` | out-message `{ fromName, body }` |
| server → client | `$exit` | `{ code, state }` |
| client → server | `$init` | init args + `parentName` / `parentIdName` |
| client → server | `$msg` | in-message `{ fromName, body }` |

## Live state and shutdown

State streams server → client, so `proc.state` tracks the remote exactly like a
local process. `STOP` flows end-to-end: `proc.send({ type: "STOP" })` → the
server's `onStopRequested` → `$exit` → the client's `proc.wait()` resolves.
